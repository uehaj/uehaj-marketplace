# レビューの開始（ガイド付きレビュー／ツリービュー）

一時ローカル HTTP サーバ（`scripts/req_review_serve.ts`）で正本からビューを配信し、
施主が記名レビュー（承認/却下/保留・コメント・AIへの追加質問）を行えるようにする。
レビュー結果は `reqlib.ts` 経由で正本へ確定的に反映される（SR-33/SR-34、ADR-005/007/008）。

## どちらのビューで開くか

- **ガイド付きレビュー（`/guided`）** — 網羅レビューにスライドを読み進める通読型。
  はじめてのレビュー・一括レビュー・裁定待ちが多いときの既定。
- **ツリービュー（`/`）** — 構造と依存を見ながらの自由巡回型。
  特定レコードの消化・依存関係の確認向き。

指示から判断できなければガイド付きを既定とする（両ビューはトップバーのタブで行き来できる）。

## 実行手順

1. **既に稼働していないか確認する**（既定ポート 8765 固定）。

   ```bash
   curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:8765/ || true
   ```

   200 が返れば起動不要。ビューはリクエストごとに正本から再生成されるので、
   そのまま手順 3 へ（URL を開くだけでよい）。

   **ただし「再生成」されるのは正本（`docs/requirements/*.md`）の内容だけである。**
   生成スクリプト（`req_tree.ts` / `req_guided.ts` / `reqlib.ts` 等）自体を修正した場合、
   Node は起動時に読み込んだモジュールをメモリに保持するため、**サーバを再起動するまで
   修正は反映されない**。稼働中サーバの起動時刻とスクリプトの更新時刻を比べて判断する。

   ```bash
   PID=$(lsof -ti :8765 | head -1)
   ps -o lstart= -p "$PID"                                    # サーバの起動時刻
   ls -l "${CLAUDE_PLUGIN_ROOT:-.}/scripts/req_tree.ts"        # スクリプトの更新時刻
   ```

   スクリプトの方が新しければ `kill "$PID"` して手順 2 で起動し直す。
   反映されたかは生成物を直接見て確かめる（例: 種別カラムの見出しを検査する
   `curl -s http://127.0.0.1:8765/ | grep -o 'class="col-label"[^>]*>[^<]*<'`）。
   「直したのに直っていない」の原因はほぼこれである（2026-07-27 の教訓）。

2. **サーバを起動する**。本体スクリプトの位置を解決して実行する。

   - プラグインとしてインストールされている場合:

     ```bash
     nohup node "${CLAUDE_PLUGIN_ROOT}/scripts/req_review_serve.ts" \
       --root "${CLAUDE_PROJECT_DIR}/docs/requirements" --no-open \
       > /tmp/req_review_serve.log 2>&1 & disown
     ```

   - このリポジトリ自身（セルフホスティング先）では:

     ```bash
     nohup node scripts/req_review_serve.ts --no-open > /tmp/req_review_serve.log 2>&1 & disown
     ```

   **必ず `nohup … & disown` で切り離して起動すること。** フォアグラウンド実行は
   セッションを塞ぎ、ツールのバックグラウンド実行はセッション境界（コンパクション等）で
   プロセスごと回収されてサーバが落ちる（2026-07-26 の教訓）。起動後、ログの 1 行目
   （`req_review_serve: http://127.0.0.1:<port>/`）でポートを確認する。ポートは 8765 固定
   （origin を安定させ localStorage の記名・進捗を再起動をまたいで保持するため。
   使用中のときのみ空きポートにフォールバックする）。

3. **ブラウザで開く**（`open` はプラットフォーム依存。開けなければ URL を案内するだけでよい）。

   ```bash
   open http://127.0.0.1:8765/guided   # 通読（ガイド付き）
   # open http://127.0.0.1:8765/      # ツリービュー
   ```

4. **施主に案内する**: レビュー中は判定・コメント・追加質問がその場で正本に反映される
   こと、`#レコードID` を付けた URL（例 `/guided#SR-34`）で特定レコードへ直接飛べる
   ことを伝える。**レビュー画面に終了ボタンは無い**（SR-61・SOL-52。施主裁定 2026-08-09
   で全廃。経緯は ADR-007 の 5 節）。判定は送信のたびに正本へ書かれるので、レビューを
   終えるときはタブを閉じるだけでよい。サーバは稼働したまま残るため、続けて他のビューを
   開く・後で同じ URL に戻って再開できる（サーバが残ること自体が SR-61 の目的である）。
   **ガイド付きレビューでは「承認」は「確認」チェックボックスで行う**（SOL-50。チェック＝
   承認で、`approval: agreed`・`confidence: confirmed`・`review_required: false` まで正本へ
   書き戻される。チェック解除は確認の取り消しで `approval: candidate`・
   `review_required: true` に戻り、取り消し記録が `meta/reviews/` に残る。SEC 自身にも同じ
   確認チェックがある）。右サイドバーに現在のレビューの全レコード ID と確認状況が一覧され、
   行クリックで該当スライドへ移動できる。サイドバー上部の「未確認のみ」フィルタは
   **既定オン**（施主指示 2026-08-09）で、確認済みの行は隠れる。確認済みも見たいときは
   チェックを外す（状態は localStorage に残る）。却下・保留・コメント・追加質問は従来どおり
   （承認だけがチェックボックスに移った）。ツリービューは従来の承認/却下/保留の3ラジオの
   ままで変わっていない。
   **ツリー・通読レビューの両画面は 5 秒ごとにサーバへ heartbeat（`GET /ping`）を送る**
   （SOL-51）。サーバが落ちる・応答しないと画面全体を覆うモーダルで「サーバとの接続が
   切れています」と知らせ、判定 UI 自体は disabled にしない（再接続すれば次の heartbeat で
   モーダルは自動的に閉じ、そのまま送信を再試行できる）。文書体裁ビュー（`/document`）は
   判定 UI が無いため heartbeat の対象外。

5. **サーバ稼働中は正本を書き換える作業やコミットを避ける**（レビューの書き込みと競合
   するため）。施主がレビューを終えたと分かったら、追加質問（meta/open-questions.md）と
   却下コメント（meta/reviews/）を読み、必要な問い直し・修正を行う。
   **稼働中のサーバを勝手に止めない。** 終了ボタンが無いため、サーバが動いていることは
   「レビューが終わっていない」ことと区別がつかない——別のタブ・別のセッションでレビューが
   進行中かもしれない。正本の編集やコミットに入る前に停止が必要なら、レビューが継続中で
   ないかを施主に確認してから `kill $(lsof -ti :8765)` を実行する（起動した端末なら
   `Ctrl-C`）。稼働したまま残すのが既定の姿である。

## レビュー観点: SOL の verification（SR-48/SOL-40）

レビュー（章節通読・ツリー巡回いずれでも）で `kind: solution_requirement` のレコードに
行き当たったら、`verification` が具体的で合否判定できる形かを見る。可能なら数値
（閾値・件数・時間等）を用いて合否を判定できることが望ましい。「〜できること」だけで
判定条件を欠く曖昧な verification（例: 主語・動作の反復や「正しく動作すること」のみ）は
指摘の対象とし、コメントで具体化を求める。本質的に数値化できない SOL は、数値でなくとも
「何をもって満たされたとするか」が判定可能な形で書かれていればよい（曖昧の指摘対象では
ない）。`req_lint.ts` の必須検査（verification 空を違反として報告）と保守的な弱シグナル
警告（極端に短い verification）はこの観点の機械的な下支えであり、質の最終判断
（具体性・合否判定可能性の妥当さ）はレビュー（人・AI）が行う。SR には本条件を課さない
（3階層の非対称性。verification 検証可能性は SOL の性質）。

## 静的 HTML だけほしいとき（配布用・オフライン下書き）

```bash
node "${CLAUDE_PLUGIN_ROOT:-.}/scripts/req_bundle.ts" --root docs/requirements --out "docs/generated/バンドル.html"
```

req gen（＝req_bundle.ts）で、文書体裁・ツリー・通読レビューを1枚に束ねた自己完結 HTML
（バンドル.html。上部ナビでビュー切替）を生成する。file:// で開ける。正本・サーバへは何も
送信されないが、判定・コメント・質問の入力自体は「オフラインモード」で行える（SOL-37）。
CSP で iframe を禁止する配信先でも動く（ADR-013。iframe 不使用）。配布先のブラウザにサーバを立てられない
場合の回収手順は次節を参照。

## オフライン下書きの回収（SR-45/SOL-37/ADR-011）

配布先（サーバを立てられないレビュアー。SIer の担当者・別部門の関係者など）が静的 HTML を
下書きモードでレビューし、「📋 すべてコピー」の出力をテキストで施主から受け取ったときの
回収手順。**回収経路はこれ（コピー→AI 解釈→dry-run→施主裁定→適用）のみで、機械適用 CLI や
サーバ接続時の自動送信は作らない**（ADR-011 の裁定。承認の最終権限は施主にあるという
SOL-16・BR-4 の裁定構造を、機械適用が迂回しないようにする）。

1. **対象の突合**: 受け取ったテキスト冒頭の
   `対象: <プロジェクト識別子> <版>（生成 <日付>）` と `レビュアー: <記名>` を確認し、
   `docs/requirements/meta/changelog.md` の先頭 `## v… — …` 見出し（現正本の最新版）と
   比較する。版が古い場合は「版ずれ」として手順3で個別に扱う。**`<版>` が `不明`（配布元に
   changelog.md が無かった、または見出しをパースできなかった場合の埋め込み値）のときは、
   版の新旧を判定できない以上、安全側に倒して全レコードを版ずれ扱いにし、手順4の一括
   dry-run 適用ではなく手順3の個別施主裁定にまわす。**

2. **写像**: 各 `## <ID>` ブロックを `scripts/reqlib.ts` の `applyReviewActions` が受け取る
   `ReviewAction`（`{ id, verdict, reviewer, comment, questions }`）に変換する。
   `判定:` の日本語（承認/却下/保留/（なし）) を `approve`/`reject`/`hold` に対応させ、
   「（なし）」は判定なし＝そのレコードはコメント・質問のみの扱いにする
   （`verdict` が無い/不正な action は `applyReviewActions` がそのレコードだけを
   エラーとして報告し、他のレコードの処理は止めない）。

3. **版ずれレコードの除外**: 手順1で版ずれがあった場合、対象 ID を
   `git log -p -- docs/requirements/<ID>.md`（またはコミット履歴・changelog の記載）で
   配布時の版以降に変更されていないか確認する。変更されていたレコードは自動写像から外し、
   「配布後にこう変わっている。この下書きの判定をどう扱うか」を個別に施主へ提示して
   裁定を仰ぐ（機械適用しない）。変更が無かったレコードは通常どおり手順4に進める。

4. **dry-run 提示**: 新しい CLI は作らず、既存の `applyReviewActions` をその場で呼ぶ
   （`req_review_serve.ts` が同じ関数をサーバ経由で呼んでいるのと同じ土台）。

   ```bash
   node --input-type=module -e '
   import { applyReviewActions } from "./scripts/reqlib.ts";
   const actions = [
     { id: "SR-12", verdict: "approve", reviewer: "<配布先の記名>", comment: "…", questions: "" },
     // 手順2で写像した残りの action …
   ];
   console.log(JSON.stringify(applyReviewActions("docs/requirements", actions, { dryRun: true }), null, 2));
   '
   ```

   出力の `results[].changes`（差分の要約）をそのまま施主に提示し、承認を得る。

5. **適用**: 施主の承認後、同じコマンドの `dryRun: true` を `dryRun: false` に変えて実行する
   （手順3で個別裁定にまわしたレコードは、施主の指示どおりに別途 action を組むか、対象外
   のまま残す）。

6. **回収元の記録**: 適用によって `applyReviewActions` は通常のとおり
   `docs/requirements/meta/reviews/<ID>.md` に判定・コメントを追記するが、これがオフライン
   下書き経由であることは自動記録されないため、適用後に当該ファイルへ一行追記する
   （例: `（オフライン下書きからの回収。レビュアー: <記名>、対象版: <配布時の版>）`）。
   版ずれで個別裁定にまわしたレコードについても、裁定の結果（適用した/しなかった）を
   `meta/reviews/<ID>.md` または `meta/open-questions.md` に残す。

## 方針分岐による一括裁定（SR-47/SOL-39）

裁定待ち（review_required・candidate・open question・矛盾）が複数たまっているときは、
1 件ずつ質問せず、まず**それらの判断を規定している上位の方針**を探して束ねる。

提示形式（必ずこの形にする）:

1. **方針の選択肢**（A / B / …）を明示する
2. 各選択肢の下で、**束ねた各項目がどう確定するか**を項目ごとの対応表で示す
   （「方針 A なら: SOL-x は承認・SOL-y は却下・OQ-z は解消」「方針 B なら: …」）
3. 方針から帰結を導けない項目は**束ねに混ぜず**、個別裁定に回すと明記する
4. 選択式 UI（review-wizard が使える場合）では、分岐帰結表を detail に添える

施主が方針を裁定したら:

- その分岐の帰結を束ねた項目へ一括適用する
- 各項目の記録（confidence_note・meta/reviews/ のスレッド）に
  **「方針裁定〈方針名〉からの一括確定」**である旨を残す（個別裁定と区別できるように。
  節一括確認の可視化と同じ思想——「考えずに確定」を不可視にしない）
