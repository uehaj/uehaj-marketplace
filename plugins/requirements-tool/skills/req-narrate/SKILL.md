# req-narrate — 文書ビュー本文（ナラティブ）の執筆

正本のレコード群を「文書のように読んで理解できる」散文に書き下ろす（SR-42・SOL-34・ADR-010）。
出力は本文フラグメントのみで、器（目次・参照様式・バルーン・スタイル）は
`req_document.ts` が決定的に合成する。**このスキルの成果物は非決定的でよい。
目的は読者に理解させることであり、レコードの転記ではない。**

## 出力の契約（フラグメント契約）

- 出力先: `<正本root>/meta/narrative.html`（既定 `docs/requirements/meta/narrative.html`）
- 中身は **`<body>` 内相当の HTML 断片**。`<!DOCTYPE>` `<html>` `<head>` `<style>` `<script>` を**書かない**
  （器が捨てる/二重になる。req-web の教訓）
- 章は `<h2>`、節は `<h3>`（`<h1>` は器が出すので使わない）。目次も書かない（器が見出しから作る）
- 冒頭に HTML コメントで生成メタを 1 行: `<!-- narrative: 生成 2026-08-01 / 正本 v0.92 時点 -->`
- レコードへの参照は段落末に弱く添える:
  `<a class="ref" data-req-link="SR-42">(SR-42, 合意済み)</a>`
  見出しに ID を入れない。リンクの解決・バルーン表示は器の責務
- 正本（`docs/requirements/` のレコード md）を**一切書き換えない**

## 対象範囲（施主裁定 2026-08-05）

ナラティブに書くのは **BR（ビジネス要求）・SR（ステークホルダー要求）・非機能要件（SEC-11 配下の
SOL）** に限る。**機能要件（SEC-10 配下の SOL）は含めない**。

理由: 非機能要件は「システムがどうあるべきか」として読み物の中で意味を持つが、機能要件は個別の
振る舞いの列挙であり、読み物より一覧・構造で見るほうが適切（ツリービュー・通読レビューで読む）。

ただし BR/SR の記述の中で「この要求はどの機能要件が受けているか」への**参照（data-req-link）は
残してよい**——トレーサビリティを文書上で切らないため。章として立てて内容を書き下ろすことを
しない、という意味である。MO（必須アウトプット）・ADR（決定の記録）の章は従来どおり含める。

## 執筆規範（読みやすさが最優先）

1. **章冒頭に概観段落**を置く。その章が全体の中で何を担い、読者が何を判断するために読むのかを先に言う。節の冒頭にも一言の前置きを置く
2. **主語と文脈を必ず補う**。レコードは文脈を前提に書かれているが、読者は前提を持たない
3. **レコード本文をそのまま転記しない**。意味を保って書き直す。ただし意味を変えない・要求を捏造しない・状態（合意/仮決め）を勝手に確定させない
4. **仮決め・未確定は散文に書き下す**: 「現時点では〜としている」「〜は候補であり、…の裁定を待っている」。バッジや生値（provisional 等）を本文に持ち込まない
5. **付録**（実装方式・必須アウトプットの詳細など規範でないもの）には冒頭に「本付録は要求仕様の一部ではない」と明示する
6. **3 段落を超えて関係を説明しそうになったら図を検討**する（インライン SVG または HTML 表。外部 URL・外部スクリプトは使わない）
7. 章立ては正本の SEC 構造を尊重しつつ、読みの流れのために順序・粒度を調整してよい（何をどの章に書いたかが追えること）
8. 長さの目安: 全体で読み切れる分量（レコード全文の複製ではなく、理解に必要な密度）

## 手順

1. 正本を読む（`docs/requirements/*.md` と `meta/changelog.md` の最新版番号）
2. 上記契約・規範に従って `meta/narrative.html` を書く（生成メタコメントに正本の版を記す）
3. `req lint`（または `node scripts/req_lint.ts`）で正本が無変更で健全なことを確認する
4. ビューを再生成して合成結果を確認する（`./bin/req gen`、または `node bin/req.ts gen`）。
   レビューサーバ稼働中なら http://127.0.0.1:8765/document のリロードで確認するよう施主に案内する
   - フラグメントがあれば器が自動で合成する
   - **フラグメントが無い場合、レコード忠実表示へのフォールバックは行わない**（施主裁定
     2026-08-05）。文書ビューの本文は「本文（ナラティブ）が未生成です」の案内パネルになり、
     生成方法（`/req-narrate` → `./bin/req gen`）とフラグメント契約が表示される。
     バンドルの生成自体は止まらないので、ツリー・通読レビューは使える。よってこのスキルの
     実行漏れは文書ビューを開けば必ず気づける
5. 執筆で気づいた矛盾・不足（書き下ろすと辻褄が合わない箇所）は、黙って直さず SR-8 の
   プロセスで施主に報告する——ナラティブ執筆は妥当性確認（読める形での吟味）の機会でもある
