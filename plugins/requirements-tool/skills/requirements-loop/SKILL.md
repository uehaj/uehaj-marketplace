# requirements-loop — 常時プロセスルール（SR-8 の自己適用）

このスキルは、施主の指示に要求・要件の追加/変更が混ざっていたら、明示的な宣言が
なくてもそれを検出し、正本（`docs/requirements/`）に反映するための手順を持つ。
プラグインは CLAUDE.md を配布できないため、このスキルと UserPromptSubmit フック
（`hooks/on-prompt-submit.sh`）が SR-8 の常時適用をプラグイン内で担う。

## 前提: 正本の構造

- 1 要求/要件 = 1 md ファイル。frontmatter に `id` / `kind` / `state` / `traces_to` /
  `axes` 等を持つ。`kind` は `business_requirement`(BR) / `stakeholder_requirement`(SR) /
  `solution_requirement`(SOL) / `mandatory_output`(MO) / `document_section`(SEC) /
  `use_case`(U)。
- 正本ディレクトリは対象プロジェクト側（既定 `docs/requirements/`）。プラグイン本体には
  一切含まれない（SR-26: 本体とプロジェクト固有データの分離）。
- 検査・生成はこのプラグイン同梱の CLI（`scripts/req_lint.ts` / `req_bundle.ts`
  （`req gen`） / `req_init.ts`）が決定的に行う。AI は結果を解釈する。

## 手順（プロンプトを処理するたびに検討する）

1. **判別** — プロンプトに新しい願望・条件・制約・目的の言明が含まれるか見る。
   主語が人・組織で述語が願望なら**要求**、主語がシステムで述語が検証可能な条件なら
   **要件**。既存要求の目的や優先関係を語る発言（「この項目は〜のためだ」等）も
   要求の更新として扱う。
2. **追記** — 検出したら `docs/requirements/` に ID を振った md を追記する
   （BR-n / SR-n / SOL-n / SEC-n。既存 ID 体系に合わせる。番号は既存最大 +1、
   欠番があっても振り直さない）。`meta/changelog.md`（存在する場合）に版として
   変更履歴を記録する。
   - **axes の仮決め付与（SOL-27）** — 新規レコードには `axes` を仮決めで埋める。
     とくに意味グループ `axes.group`（自由記述の日本語グループ名）を statement の
     意味から起こして付与し、`axes.review_required: true` を立てる（施主の承認・訂正
     待ちの印。SR-9「属性付与は AI・施主は承認訂正のみ」＋ SR-19「仮決め＋レビュー
     必須マーカー」の運用）。既存レコードの `axes.group` の値の集合を見て、合う群が
     あればその名称を再利用し、無ければ新しい群名を提案する（乱立を避ける）。BR は
     群化しない（件数が少ないため）。group を空のまま追記しない（ツリービューで
     「未分類」に落ちるため）。付与した group と review_required は §6 の報告に含める。
   - **SOL の verification は検証可能な形にする（SR-48/SOL-40）** — `kind:
     solution_requirement` を追記するとき、`verification` は具体的で、可能なら
     数値（閾値・件数・時間等）を用いて合否を判定できる形にする。「〜できること」
     だけで判定条件を欠く曖昧な verification は差し戻す/指摘する（自分が書いた
     ものであっても、書いたその場で見直す）。本質的に数値化できない SOL は、
     数値でなくとも「何をもって満たされたとするか」が判定可能な形であればよい。
     `req_lint.ts` は verification が空（null/空文字/空白のみ）を違反として報告し、
     極端に短いものは保守的な閾値で警告する（機械層）。質の最終判断（具体性・
     合否判定可能性）は AI・人が行う（意味層）。SR には課さない（3階層の非対称性）。
3. **検査** — 追記後、CLI で検査する。

   ```bash
   node "${CLAUDE_PLUGIN_ROOT:-.}/scripts/req_lint.ts" --root docs/requirements
   ```

   （`CLAUDE_PLUGIN_ROOT` が未設定の場合は、このリポジトリ自身での直接実行を想定し
   カレントディレクトリの `scripts/req_lint.ts` を使う。）

4. **矛盾検査** — 既存の要求・要件と矛盾しないか、緊張関係がないかを見る。矛盾が
   あれば握りつぶさず施主に提示し、裁定を仰いで解消する（裁定者は常に施主）。
5. **不足検査** — 新要求がトレーサビリティの穴を作らないか（`traces_to` が実在の
   親を指しているか、逆に既存要求がどの要件からもカバーされないままにならないか）
   を確認する。`req_lint.ts` の出力（`[trace]` `[tree]` 等のタグ）を根拠にする。
6. **報告** — 検出・追記・検査の結果を応答の中で施主に報告する。黙って書き換えない。
   「今回の指示から SR-n を抽出した。既存と矛盾なし／裁定が必要な点がある」の形。

## ビューの再生成

正本を変更したら、必要に応じてバンドル（文書・ツリー・通読レビューを束ねた単一 HTML）を
再生成する（`req gen` 相当。プラグイン導入先では `req` が PATH 上にない前提のため、
`scripts/req_bundle.ts` を直接呼ぶ）。個別ビューの HTML はもう生成しない。

```bash
node "${CLAUDE_PLUGIN_ROOT:-.}/scripts/req_bundle.ts" --root docs/requirements --out docs/generated/バンドル.html
```

## 初期化（インストール直後）

対象プロジェクトにまだ `docs/requirements/` がない場合は `/req-init` コマンド
（このプラグインの `commands/req-init.md`）を使い、必須アウトプットカタログの
投入と正本ディレクトリの作成を行う。

## 理論的な注意

- 個々の要件は必要条件、要件セット全体は十分条件の仮説。必要性はトレーサビリティで
  機械的に検査できるが、十分性は妥当性確認（validation）でしか確かめられない。
- 要求と要件の対応は N:M。1 対 1 を前提にした表や文言を書かない。
- どの要求にも遡れない要件は過剰仕様の疑い。削る候補として施主に提示する。

## 裁定の束ね方（SR-47/SOL-39）

矛盾・仮決め・不足の裁定を施主に仰ぐとき、裁定待ちが複数あれば「大きな方針 → 項目別の
帰結」の分岐つき質問に束ねる（req-review スキルの「方針分岐による一括裁定」の形式に従う）。
1 件ずつの質問の羅列は、方針で束ねられないと確認できた項目に限る。

## 固有名称の扱い（SOL-43）

ビュー名・機能名などの固有名称を新しく導入する、または変更するときは、SEC-4「用語・概念」
本文の「固有名称の辞書」を必ず更新する。ビュー・スキル・コマンド・生成文書の利用者向け
文言は辞書の正式名称に従い、黙って別表記を増やさない。
