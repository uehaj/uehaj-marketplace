# req-issues — イシューリコンサイル（SR-57・SOL-48・ADR-014）

正本と実装状態のギャップからイシュー群を収束させる。**発行（generate）ではなくリコンサイル
（あるべき状態への収束）**——ギャップが存在する間だけイシューが存在し、消えたら閉じる（提案まで）。
**施主の明示起動でのみ実行する**（イシュー群への一括書き込みのため。ADR-009 の 4 面規約）。

構成は「算出（機械的）→ 突合・判断（AI）→ 適用」。算出は `req gaps`（`scripts/req_gaps.ts`。
決定的 CLI）が担い、本コマンドは突合と配置を担う。

## 配置先（本コマンドは置き場所を持たない）

イシューをどこに置くかは**プロジェクトの issue-tracker 規約に委譲**する（施主裁定 2026-08-08。
ADR-014 Q1）。実行時にまず配置先を特定すること:

1. プロジェクトの CLAUDE.md・`docs/agents/issue-tracker.md` 等でイシュー管理の規約を探す
2. 規約が見つからなければ、施主に配置先を確認してから進める（勝手に方式を発明しない）
3. 本リポジトリ（セルフホスティング）ではローカル md 方式:
   親（U）＝ `.scratch/<U-slug>/`、子イシュー＝ `issues/NN-<slug>.md`、
   孤児集約＝ `.scratch/requirements-orphans/issues/01-orphans.md`

## 実行手順

1. **ギャップ算出**: `node "${CLAUDE_PLUGIN_ROOT}/scripts/req_gaps.ts"
   --root "${CLAUDE_PROJECT_DIR}/docs/requirements" --json` を実行し、ギャップ集合を得る。
   `type: review` のギャップは**スキップする**（レビュー面の管轄。通読レビュー・req-status で
   扱う。イシューにしない——ADR-014 Q4）。対象は `unimpl` と `orphan` のみ。

2. **既存イシューとの突合**: 配置先のイシューを走査し、`Key:` 行（下記 5 則の 1）で突合する。
   タイトル一致などの曖昧マッチは禁止。結果を 3 群に分ける:
   - **作成**: ギャップにあり、対応する Key のイシューが無い
   - **更新**: Key が一致し、ギャップの `hash` とイシュー内の generated 領域の hash が異なる
   - **クローズ提案**: Key のイシューがあるが、対応するギャップが消えている

3. **dry-run の提示**: 作成/更新/クローズ提案の一覧（Key・対象レコード・親 U・理由）を施主に
   提示し、承認を得てから適用する。0 件なら「収束済み」と報告して終了。

4. **適用**: 配置先の規約に従って書き込む。トラッカーが何であれ次の **5 則**を守る（SOL-48）:

   1. **安定キーの必記**: イシュー冒頭付近に `Key: unimpl:SOL-46` 行（外部トラッカーなら
      ラベル/外部 ID）。次回以降の突合はこのキーのみで行う
   2. **生成領域と人間領域の分離**: 要求の転記（statement・verification）は
      `<!-- generated (hash: a3f9c1d2) -->` 〜 `<!-- /generated -->` に置き、更新時は
      **この領域だけ**を書き換える。人間領域（実装メモ・`## Comments`）には一切触れない。
      領域内の先頭に権威の方向を明記する:
      「この領域を編集しても要求は変わりません。正本: docs/requirements/SOL-46.md」
   3. **更新はハッシュ比較で**: 生成領域を新しい内容と hash に置き換え、`## Comments` に
      「着手中に要求が変わった」旨の警告（旧 hash → 新 hash、日付）を追記する
   4. **クローズは提案まで**: イシューを削除・クローズせず `Status: ready-for-human` に変え、
      `## Comments` にクローズ提案と根拠（どのギャップがどう消えたか。例: implementation が
      implemented になった）を追記する。確定は施主（SOL-16 と同じ原則）
   5. **冪等性**: 同じ状態で再実行したら変更 0 件になること。適用後に手順 1〜2 を再実行して
      0 件を確認するとよい

   新規イシューの本文構成（ローカル md の場合）:
   ```markdown
   # SOL-46 通読レビューのユースケースレビューモード
   Key: unimpl:SOL-46
   Status: needs-triage

   <!-- generated (hash: a3f9c1d2) -->
   この領域を編集しても要求は変わりません。正本: docs/requirements/SOL-46.md

   ## 実装対象
   （statement の転記）

   ## 受け入れ条件
   （verification の転記）

   関連ユースケース: U-03, U-05   ← 複数 U に遡られる場合のみ。親は ID 最小の U
   <!-- /generated -->

   ## 実装メモ

   ## Comments
   ```
   孤児集約イシュー（`Key: orphan`）は generated 領域に対象レコードの一覧（ID・タイトル）を
   持ち、毎回の実行で一覧を最新化する。

5. **報告**: 作成/更新/クローズ提案の件数と一覧、スキップした review ギャップの件数（レビュー面
   への誘導つき）、孤児の増減を施主に報告する。イシューに要求の追加・変更が現れていたら SR-8 の
   プロセスに従い正本へ反映する（イシューは作業チケットであり要求の正本ではない）。

## 注意

- 本コマンドは正本（docs/requirements/）を書き換えない（書くのはイシューのみ）
- 自動クローズ・フックによる自動起動はしない（ADR-014 で却下済み。理由もそちらに記録）
- MO（納品系）・非機能制約の注入は v1 対象外（SR-55 採否待ち。ADR-014）
