# 必須アウトプット カタログ（SR-25）

どのプロジェクトでも最終的に確定させるべき事項（境界 API・テクノロジースタック等）の
定型要件カタログ。`scripts/req_init.ts` がプロジェクト開始時に各項目を**未決レコード**
（approval=candidate / confidence=undecided）として `docs/requirements/` へ投入する。
未決の必須アウトプットは EC-1/2/5/17 系の問い（いつ決めるか）の監視対象＝駆動の燃料になる。

## ツール本体とプロジェクト正本の分離（SR-26）

このカタログは**ツール本体側**の資産であり、アップデートで更新される。投入された
MO レコードは**プロジェクト側**（docs/requirements/）の資産であり、アップデートで
上書きされない（req_init は既存 ID をスキップする冪等な橋渡し）。この分離線が
アップデートの互換性契約になる。

## 運用ルール

- **非該当の扱い（施主裁定 2026-07-05）**: プロジェクトに該当しない MO は削除せず、
  approval=rejected の要件として保持する（INV-1 により disposition は active 以外へ変更する。
  例: disposition=obsolete）。却下の判断自体が後日の再考の入口になる（SR-24 と整合）。
- 各項目の axes は AI 仮決めのプリセット（全件 review_required: true）。投入先プロジェクトで
  施主がレビューして確定する。**group もこのプリセットに含む**（2026-08-14 追加）——
  SOL-27 は「新規レコードには group を仮決めで付与し review_required を立てる。未設定だと
  ビューで『未分類』に埋もれる」と定めており、配布物もその規約に従う。group が空のまま
  配ると、投入先は初期化した瞬間から lint の警告を抱える（実際に別プロジェクトで 9 件発生。
  changelog v0.146）。
  group の値はツールの文脈で付けた仮決めなので、投入先の意味グループ体系に合わない場合は
  施主がレビューで付け直してよい（review_required: true はそのための印である）。
- カタログへの項目追加・修正は AI 提案・施主裁定で行う（SR-18 と同じ淘汰運用）。
