# レビューとマージ、サブエージェント

## 流れ

1. 実装担当が完了を報告する（ブランチ、head SHA、PR、実行した確認）。
2. レビューは実装担当と別にする。既定は、最も強いモデルのサブエージェントを worktree 隔離（`isolation: "worktree"`）で
   起動し、批判的レビューをさせる。指摘は重大・中・軽に分けさせ、最後に「マージ可 / 不可」を書かせる。
3. レビュー結果は最終報告に全文で返させる。worktree が片付くとそこに書いたファイルは消えるので、
   コーディネーターが受け取った全文を `workdir/review-<PR>.md` に書く。
4. 重大・中の指摘があれば、担当に伝えて直させ、同じ条件（同じモデル、同じ観点）で再レビューする。
5. 「マージ可」でも、ユーザーがその条件でマージしてよいと決めているときだけ進める。リポジトリにレビュー記録の仕組み
   （ステータスを付けるスクリプト、必須チェック、ラベルなど）があれば、その規約どおりに記録してからマージする。
6. 外部の人の PR、またはそのコミットを含むブランチは、レビュー結果とマージ方法（そのまま / 修正を足して / 閉じる）を
   示してユーザーの承認を取る。PR へのコメントやクローズも文面を示してから。

## サブエージェント

- 結果を次の会話に持ち越せない。最終報告に必要なことを全文で書かせる（要約だけを返させない）。
- 完了通知が来ても、「自分が裏で起動した作業の完了待ち」で途中のことがある。報告の中身を見て判断する。
- 長引くときは、SendMessage で「いまの確認結果で最終報告を出して」と促す。
- 権限の判定（auto mode の分類器など）に拒否されたら、回避させずユーザーに報告する。CLAUDE.md や設定の編集は
  自己変更として拒否されうる。

## 質問しない依頼の書き方

バックグラウンドのセッションとサブエージェントには、依頼文に次を入れる。

```text
AskUserQuestion は使わない。判断が要るところは推奨案で進め、選択肢と理由を最終報告に書く。
ユーザーの合意が要る変更（公開 API・データ形式の破壊的変更、課金、破壊的操作）は実装せず、
before / after の案を報告して止まる。
```

再開や再依頼では、元の依頼文をそのまま渡す。「元の依頼を続けて」は、別の依頼と取り違えられる。
